# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

kurly is a Jsonnet library of Kubernetes workload recipes. You start from a base kind (`http`, `worker`, `cron`, `daemon`) and add capabilities as composable `+` features (`kurly.store`, `kurly.config`, `kurly.expose.gateway`, `kurly.security.baseline`, …) — each a `{ config+:: … }` mixin, so they late-bind against the merged config in any order. Built on k8s-libsonnet. It publishes as the single-layer OCI image `ghcr.io/metio/kurly` (JOI-shaped: `FROM scratch`, jb-vendor-tree layout under `/github.com/metio/kurly/`), consumable by [jaas](https://github.com/metio/jaas) as a Flux `OCIRepository` source or an image-volume mount (author a workload as `function(params) …` and JaaS feeds the params as TLAs), and locally via `jb install`.

## Common commands

The toolchain and the dev-task commands are defined once in `flake.nix` and version-pinned by `flake.lock` (Renovate-maintained): CI runs every gate through the flake's devShell, so a gate that is green locally is green in CI by construction. Each multi-step gate is a `writeShellApplication` command (a `scripts/<name>.sh` file wrapped by nix — shellchecked at build, hermetic `runtimeInputs`), on `$PATH` inside `nix develop` and callable one-shot. There is no host task-runner (no `just`/Makefile wrapper) — the commands live in the shell they run in.

```shell
nix develop --command verify           # every gate, serially — the local pre-push check (what CI runs)
nix develop --command check-fmt        # jsonnetfmt --test across all sources
nix develop --command check-tests      # jb install + assertion suite + the requiresService/exclusion negative checks
nix develop --command check-catalog    # regenerate the derived catalog data and fail on drift
nix develop --command check-readme     # the generated README sections still match
nix develop --command check-assembler  # the docs site's assembler emits Jsonnet/YAML that parses
nix develop --command check-coverage   # every feature is exercised by a test
nix develop --command check-examples   # render examples + workloads, validate with kubeconform
nix develop --command check-readme-examples  # render the workload READMEs' deploy examples, validate with kubeconform
nix develop --command check-security   # kurly's Rego invariants (conftest) + pluto (deprecated APIs) + kubesec
nix develop --command reuse lint       # the single-tool gates call the tool directly:
nix develop --command yamllint .
nix develop --command actionlint       # shellcheck rides in the devShell, so run: blocks are linted too
nix develop --command markdownlint-cli2 '**/*.md' '#vendor'
nix develop --command typos
```

The `gen-*` commands write the derived data the gates then check: `gen-maturity`
(maturity tiers), `gen-readme` (the workload READMEs' generated section),
`gen-smoke` (one e2e scenario per workload), `gen-docs-data` (the docs site's
catalog). Several hit the network or a cluster and are therefore run on demand or
on a schedule, never in the per-PR gate: `gen-architectures` (skopeo),
`gen-signatures` (cosign; takes `STAGES=…` to re-ask a subset),
`gen-spdx` (the SPDX register, offline, rerun by `check-catalog`), `gen-upstream` (image labels — hours against a rate-limiting registry, so it
writes results incrementally and takes `WORKLOADS=…` to re-ask a subset), and
`gen-bsi` (a kind cluster).

Or drop into the shell — `nix develop` prints the command menu on entry, then run `verify` / `check-*` / any tool (`jsonnet`, `jb`, `kubeconform`, …) bare. Plain `nix-shell` works too (`shell.nix` reuses the flake via flake-compat, pinned through `flake.lock`).

On this host, `nix` is [nix-portable](https://github.com/DavHau/nix-portable) (`~/.local/bin/nix`, store in `~/.nix-portable` — user-level, no system install) and needs `NP_RUNTIME=bwrap` (exported in `~/.bashrc`; the auto-selected runtime cannot nest the build sandbox's mount namespace here). A system-level nix install is not possible on this Fedora Atomic host (the transient-root workaround broke boot). From a sandboxed shell, where nix-portable's user namespaces are blocked, resolve the same flake through the nix container image: `podman run --rm -v "$PWD:/work:z" -v metio-nix:/nix -w /work docker.io/nixos/nix:latest` with `NIX_CONFIG='experimental-features = nix-command flakes'`. **direnv is not usable here** — nix-portable's store is namespace-local, so an exported devShell env references `/nix` paths the host can't see; `nix develop` is the workflow. A contributor with a real nix install may add a local, gitignored `.envrc` (`use flake`) if they want direnv auto-loading.

jsonnet-lint is deliberately not part of the gate: it cannot resolve the vendored k8s-libsonnet's internal `doc-util` imports (jb `legacyImports: false`) and drowns real findings in vendor noise.

**Kubernetes static analysis (`check-security`)** is weighted toward custom policy. `policy/*.rego` holds kurly's own invariants, run over the RENDERED manifests with **conftest** — Rego reads the JSON jsonnet emits, so it enforces structural guarantees the general tools can't express (the managed-by label, tag-pinned images, stable selectors, volume/mount consistency), green by construction since they hold for every workload regardless of composed features. Backing it are two small, fast, no-config tools: **pluto** (removed/deprecated API detection) and **kubesec** (a security risk score with a floor the hardened defaults clear at 7-11). The heavier best-practice scorers (kube-score/kube-linter/trivy) are deliberately NOT used — they demand a large ignore-list of the deployment-topology checks a workload-recipe library does not emit, and Rego covers kurly's real contract precisely instead. The security-relaxation examples (`legacy`, `cron`) are exempt from the kubesec score (they exist to demonstrate the escape hatches) but still policy-checked.

**ASK THE CATALOGUE, NEVER THE SOURCE.** Every tool around the workloads —
`gen-smoke` above all — reads what it needs about a stage from `catalog.json`,
never by grepping the stage's jsonnet. The catalogue is DERIVED from those files
and its annotations are drift-checked against them (`check-catalog` fails when an
annotated default disagrees with the real one), so it is both authoritative and
verified; a grep is neither. A pattern match reads only what happens to be
spelled the way it expects and answers "absent" for everything else, which is
indistinguishable from a fact that genuinely is not there.

The cost is not hypothetical. `piler` declares `engine: mysql` and takes its
connection details from a Secret, so a grep of its source for `3306` found
nothing and the harness provisioned a PostgreSQL; the workload then reported that
it could not reach its database, which reads as the workload's defect. `traduora`
was handed the same wrong engine AND the PostgreSQL host-naming convention, so it
timed out against a Service with nothing behind it.

Where the catalogue does not know a fact, the answer is to RECORD IT THERE — not
to guess from the file. A generator that must fall back prints the stage it
guessed for, so the gap gets annotated instead of being rediscovered later by a
workload that will not start.

**Live-cluster e2e** is the real-cluster complement, in two tiers. The FAST tier is one scenario per catalogued workload, `hack/smoke/scenario-<id>.sh`, generated by `gen-smoke` from the catalog and marker-guarded (a hand-written scenario is never clobbered): render the stage's defaults as a consumer would, apply, wait for every controller to become healthy — a custom-resource stage is server-side dry-run against the real operator schema instead. `hack/smoke/lib.sh` carries the shared helpers: `kurly::boot`, throwaway dependency provisioners (`kurly::postgres` — with a `pg_isready` readiness probe, because an app that connects once and panics races it — `kurly::mysql`, `kurly::mongodb`, `kurly::cache`, `kurly::objectstorage`), `kurly::secret` (minting a Secret from the catalog's `secretKeys`; generators `password`/`hex`/`base64`/`base64url`/`literal`/`postgresUrl`/`redisUrl`/`mysqlUrl`), and `kurly::validate_cr`. An app that cannot start without a deployment-specific value (its own public URL) gets it from `hack/smoke/extra.json`, composed onto the stage by the generator, rather than the workload carrying a default that would be wrong everywhere it is really deployed. The DEEP tier is `hack/smoke/deep/*.sh`: hand-written scenarios proving a seam BETWEEN workloads (a migration ladder through Flux/JaaS/stageset, a CNPG backup into SeaweedFS, a distributed SeaweedFS) — they stand up a registry and operators, so they are run deliberately and are not part of the per-workload walk.

**A POD STUCK IN `ContainerCreating` MEANS `hostUsers: false`, AND NOTHING ELSE.**
The local cluster is kind on **rootless podman**, which cannot nest a user
namespace, while kurly's `restricted` default gives every pod its own — so every
render carries `hostUsers: false` and no such pod can start here. The error names
neither:

```
failed to create network namespace for sandbox "…": failed to start noop process
for unshare: fork/exec /proc/self/exe: operation not permitted
```

`kurly::boot` already composes **`+ k.hostUsers()`** onto every stage, which is
why scenarios work. A hand-applied render must do the same, or it cannot start:
`k.list(w() + k.hostUsers())`. Prefer running `hack/smoke/scenario-<id>.sh` over
applying a render by hand at all. This has been misdiagnosed here as the cgroup
PID ceiling, the inotify budget, a leaking node, a host kernel regression, SELinux
and the agent's Bash sandbox — costing cluster recreations, node restarts and a
withdrawn e2e claim. It is none of those.

**A walk runs under a resource ceiling, and refuses to run without one.** An
unbounded fleet walk has taken this host to the point of being unusable, so the
budget is declared rather than hoped for, in two halves that do not share a
mechanism. The HARNESS (renders, image pulls into the podman store, kubectl)
re-executes itself inside `kurly.slice` — declared in `hack/smoke/kurly.slice`,
installed by `fleet-run.sh` — and `assert_bounded` reads the limits back out of
the kernel before anything starts, because systemd accepts a property it cannot
enforce without complaint. The NODE carries its own budget from `cgroup_conf` in
the `kube-cluster` wrapper's containers.conf, and the wrapper refuses to hand
over a cluster whose limits did not take effect. The two are separate because a
rootless container does NOT inherit the slice that launched it: podman creates it
in its own transient scope under `user.slice`, so a `systemd-run --slice=` around
`kind create` bounds the creating process and nothing that survives it.

Two measured facts shape the numbers. The io limit must name the **whole disk**
(`nvme0n1`, 259:2), never the partition the store sits on (259:5) — the io
controller accounts per block device and a cap on a partition is accepted in
silence and throttles nothing. And on btrfs that cap is **approximate**: much of
the write path is issued by the filesystem's own kernel threads, which are not
attributed to the cgroup that caused them, so a 50M cap measured 114 MB/s against
a device that does 285. The CPU and memory ceilings bind exactly and carry the
weight; the io cap is worth setting and is not worth trusting alone.

Cleanup is part of the contract: a scenario's namespace goes, and so do the cluster-scoped objects a workload leaves behind (`bollwerk`'s admission policies would otherwise govern everything booted after it; a stale `metrics.k8s.io` APIService breaks namespace deletion cluster-wide). A cluster add-on states its own namespace, so cleanup removes its objects by label wherever they live.

## Architecture

The library's entry point `main.libsonnet` lives at the **repo root** so the jb import path is `github.com/metio/kurly/main.libsonnet` — the same path the OCI image serves via jaas's vendor-tree search, keeping local and in-cluster imports identical. The recipe modules it imports (`base`, `features`, the workload kinds, `expose`, `security`, `migrations`, `k`) live under **`lib/`** and are reached as `import './lib/…'`. The library image therefore ships `main.libsonnet` **and** the whole `lib/` tree — an image with only `main.libsonnet` fails the first `import './lib/…'` a consumer triggers (a single COPY of both, staged so the image stays one layer; see the `Containerfile`). Deployable workloads live under **`workloads/<name>/`** as one `<stage>.libsonnet` per stage — a `function(params)` returning a COMPOSABLE app (a base with defaults, no exposure), which a consumer imports by canonical path, adapts with `+` features, and renders with `kurly.list`; plus a `README.md` showing the end-to-end deploy (import → JaaS `JsonnetSnippet` referencing the kurly `JsonnetLibrary` → stageset `StageSet`). Each workload directory is an independently released unit (see CI below), so the library must stay at the root and workloads must stay in their directories.

- `k.libsonnet` — the single pin of the k8s-libsonnet API version (a directory like `1.35`); every module imports k8s-libsonnet through this file, so a version bump is one line.
- `base.libsonnet` — the shared core: a hidden `config::` object, the manifest fields computed from it (`container`/`podSecurity`/`podVolumes`, the `deployment`/`service`/`cronjob`/`daemonset` bodies, the owned `storeClaim`/`configMap` handles), plus the exclusion-group `assert`. Holds **no** `with*` methods — capabilities live in `features.libsonnet`.
- `features.libsonnet` — every capability as a `+`-composable function returning a `{ config+:: … }` mixin (`kurly.store`, `kurly.config`, `kurly.secretMount`, `kurly.scratch`, `kurly.runAs`, `kurly.recreate`, `kurly.args`, `kurly.env`, `kurly.probes`, `kurly.resources`, `kurly.replicas`, `kurly.startupProbe`, `kurly.disableServiceLinks`, the security hatches, …). A feature only ever writes `config`, never a manifest, so the computed fields late-bind against the merged config regardless of compose order.
- `http|worker|cron|daemon.libsonnet` — one workload kind each, a `function(name, image)` (cron also takes a `schedule`) that composes `base.core` + the kind's mixins/manifests. These are the base "defaults" you add features onto.
- `expose.libsonnet` — exposure recipes composed onto a `kurly.http` app with `+`: `ingress` (Ingress API), and for the Gateway API `gateway`/`listenerSet` (attach an HTTPRoute to an existing parent) and `ownGateway`/`ownListenerSet` (generate the parent too). **Workload and exposure are deliberately two separate composable axes — do not fold routing back into a workload kind or add a mode toggle.** Every Gateway API recipe emits an HTTPRoute. Each recipe captures its `host` argument lexically. A shared `requiresService` object-level assert fails composition onto Service-less kinds, and **all five join the `exposure` exclusion group** so composing two fails the render (see the exclusion mechanism below). The Gateway API objects are plain manifests (no gateway-api-libsonnet) to keep consumers' render-time dependency closure at k8s-libsonnet alone; ListenerSet is GA (`gateway.networking.k8s.io/v1`, Gateway API ≥ 1.5), and the shared Gateway a ListenerSet attaches to must opt in via `spec.allowedListeners`.
- `security.libsonnet` — the Pod Security Standards profiles (`restricted`/`baseline`/`privileged`) as composable mixins, same axis pattern as `expose`. Each profile sets **every** security knob in `config`, so the last profile composed wins and the single-knob hatches fine-tune after it. `baseline` relaxes only what `restricted` requires beyond baseline and keeps kurly's extra hardening (read-only rootfs, user namespaces); `privileged` emits no security fields at all. The ServiceAccount-token automount rule is deliberately outside every profile (it is SA hygiene, not PSS).
- **`kurly.alerts()`** — a `monitoring.coreos.com/v1` `PrometheusRule` bound to THIS workload's own objects. The PromQL is the easy half; the hard half is the selectors, and kurly named every object they must match (the controller, the container, each claim), so it binds them. **A StatefulSet's claims are `<template>-<set>-<ordinal>`, generated by Kubernetes at scale-out, so those match by PATTERN and the template name is READ BACK OFF THE RENDERED OBJECT** rather than re-derived — a copy of the stateful kind's naming rule would go quietly wrong the day it changed, leaving a selector that matches nothing. **A rule that CANNOT fire is never emitted** (no memory rule without a memory limit, no storage rule without a claim, no availability rule for a controller kind lacking a ready-versus-desired metric pair), because such a rule reads as coverage on a dashboard and is not; all rules off emits no object rather than an empty one. Every rule names the [gumshoe](https://github.com/metio/gumshoe) book that investigates or fixes it as `annotations.runbook` (the command), and a `runbooks` base URL turns that into the `runbook_url` an Alertmanager UI links — absent by default, because where a team keeps its books is not kurly's to assume. `namespace` scopes the expressions: without it, or without `enforcedNamespaceLabel` on the scraping Prometheus, a rule matches this workload's name in EVERY namespace. `for`, `storageFull` and `memoryPressure` are SLO decisions and stay the caller's.
- `network.libsonnet` — allow-list NetworkPolicy as a composable axis (same pattern as `expose`), with one recipe per CNI: `kubernetes` (`networking.k8s.io/v1`), `calico` (`projectcalico.org/v3` — never the v1 storage CRD), `cilium` (`cilium.io/v2`). Rules are written ONCE in a small neutral vocabulary (`allowFrom`/`allowTo` entries of `{ pods, namespaces | namespace, cidr, ports }`) that each variant **translates** into its native kind; anything the vocabulary does not cover passes through **verbatim** via each variant's escape hatch (`ingress`/`egress`/`extraSpec`) — kurly does not model the full CNI schemas (they would drift). Every variant emits ONE policy named after the workload, selecting its own pods, and all three join the shared `networkPolicy` exclusion group (a workload firewalls one way). The low-level `kurly.networkPolicy()` feature is the Kubernetes variant taking verbatim rules; it feeds the same `config.networkPolicy` slot and joins the same group. The base's `networkPolicy::` field dispatches on the slot's `variant` and always unions in a sidecar's `requiredEgress`. The cluster-/namespace-wide default-DENY baseline is NOT baked into a workload's policy — it is offered as the standalone `kurly.network.denyAll.{kubernetes,calico,cilium}(global=…)` generators, dropped into a manifest set with `kurly.list`, so an operator picks it once for the cluster or per namespace.
- **`kurly.shutdown(drain, grace, preStop)`** — the two halves of a graceful stop set TOGETHER, because either alone is how a rolling update drops requests. Endpoint removal and SIGTERM are dispatched CONCURRENTLY and neither waits for the other, so `drain` seconds of doing nothing before SIGTERM is what lets the endpoint change propagate while the container is still serving. **The drain is spent OUT OF the grace period, not added to it** — both clocks start when the pod is doomed — so `drain >= grace` is REFUSED rather than rendered, since it leaves the application zero seconds to stop, the exact opposite of the intent. The drain uses Kubernetes' **native `sleep` handler**, never `exec: ["/bin/sh","-c","sleep N"]`: on a distroless or scratch image there is no shell, the exec fails, and a failed preStop hook stops nothing and raises nothing anybody sees — no drain, no error, a rollout quietly dropping connections. `check-coverage` renders it on every kind and validates with kubeconform, which is what confirms the field exists in the pinned schema rather than a claim in a comment.
- `backup.libsonnet` — getting a workload's volumes off the cluster, as a composable axis. **The two tools disagree about SCOPE and the axis mirrors that** rather than papering over it: VolSync is per CLAIM (a `ReplicationSource` names one `sourcePVC`, so `kurly.backup.volsync(repository=…)` emits ONE PER VOLUME the workload owns — a two-volume workload emitting one source would back up half of it and report success), while K8up is per NAMESPACE (a `Schedule` backs up every claim it finds, so a workload has nothing to opt INTO; `kurly.backup.k8up()` writes the inclusion marker on the claim EXPLICITLY anyway, because a default is a thing nobody decided, and `kurly.backup.exclude()` is the same mechanism saying leave this out — the `Schedule` itself stays a workload, `workloads/k8up/schedule.libsonnet`, placed with `kurly.list` like `network.denyAll`). A StatefulSet's per-pod claims are enumerated as `<template>-<set>-<ordinal>` from the replicas BEING RENDERED, so a set scaled out later has volumes no source covers until it is rendered again — a real limit, stated rather than hidden behind a source pointing at a claim that does not exist. Claim markers merge UNDER the store's own annotations, so a consumer who set the key by hand is not overruled. All three join the `backup` exclusion group. **Neither restores**: restoring is an operation you run once at the worst possible moment, so it stays a workload of its own (`volsync/restore.libsonnet`, `k8up/restore.libsonnet`) and the deep-tier scenarios prove the round trip by destroying a volume and reading the file back.
- `mesh.libsonnet` — service mesh as a composable axis (same pattern as `expose` and `network`): `kurly.mesh.istio()` puts the sidecar injection marker on the POD template (under the consumer's own `podLabels`/`podAnnotations`, so an explicit opt-out still wins) — **a LABEL for Istio, not an annotation**: Istio's MutatingWebhookConfiguration selects on labels only, so in a namespace carrying neither `istio-injection` nor `istio.io/rev` the annotation form injects nothing and does so silently (Linkerd's injector reads an annotation, which is why the config slot carries both `injectLabels` and `injectAnnotations`) **and** emits a `security.istio.io/v1` `PeerAuthentication` named after the workload, selecting its own pods, `mode: STRICT`. The second half is why it is a recipe rather than a one-liner: injection was always `kurly.podAnnotations`, while the enforcing object is **the half no admission policy can supply** — a `ValidatingAdmissionPolicy` sees the object being written, so it can neither observe traffic nor require another object exists, which is why `bsi` is structurally silent about mTLS. `mtls=null` emits no policy (the namespace/mesh default stands), `inject=false` suits a namespace-labelled cluster, and `peerAuthentication` merges verbatim. **No `AuthorizationPolicy`** — which principals may call which paths depends on what else a tenant runs, and the schema moves; same restraint the network axis takes with the CNI schemas. `kurly.mesh.linkerd()` says the same thing entirely in ANNOTATIONS and emits NO manifest — `linkerd.io/inject: enabled` (its proxy-injector webhook is called for every pod in every namespace that has not opted out, so there is no namespace to label first) plus `config.linkerd.io/default-inbound-policy: all-authenticated`, which is Linkerd's whole equivalent of a STRICT PeerAuthentication. Both recipes are proven end to end (`mesh-istio.sh`, `mesh-linkerd.sh`: injection, the meshed path, the refusal, and the refusal disappearing when enforcement is withdrawn). Three traps are pinned in those scripts, each having cost a wrong verdict: the POSITIVE control runs BEFORE the refusal check (an earlier ordering asserted the refusal first and passed against a port nothing was listening on); **Linkerd exempts a pod's DECLARED PROBE PATH from authentication by design** (a default `probe` authorization, so kubelet probes are not broken — probing `/` and then testing `/` asks about the one exempt path); and **Linkerd refuses with a 403 where Istio closes the connection**, so the reachability check reads the HTTP STATUS, never curl's exit code, which is zero on a 403. Each recipe keeps its mesh's OWN vocabulary rather than a shared invented one (`STRICT` means nothing to Linkerd, `cluster-authenticated` has no Istio equivalent); the neutral promise is at the recipe — `kurly.mesh.<mesh>()` with no arguments means meshed, plaintext refused, in both. Both take `proxyImage`, because Istio publishes from `registry.istio.io/release` and Linkerd from `cr.l5d.io`, neither of which an allow-list cluster permits nor an air-gapped one can reach; **`kurly.mirror` rewrites those annotation values too** (`sidecar.istio.io/proxyImage`, `config.linkerd.io/proxy-image`) — the image is pulled by a container that does not exist when mirror runs, so leaving them out mirrors the workload and leaves its sidecar on the public internet. Both meshes program pod iptables from a PRIVILEGED init container by default and both offer a CNI plugin that moves it to a node agent (`mesh-bsi.sh <mesh>` measures the difference; the injected containers cost 4 policies for Istio and 3 for Linkerd, falling to 1 and 2 with the plugin, while the node agent that takes over breaks 9 and 7) — **after enabling the plugin the scenario RE-ADMITS until the init container actually disappears**, because helm returns once the control plane is Ready while the injector may not yet serve the new config, and a pod admitted in that window carries the old shape with every command exiting zero. Recipes join the `mesh` exclusion group; the namespace-wide floor is the standalone `kurly.mesh.strictNamespace.istio()`, placed with `kurly.list` like `network.denyAll` — there is no linkerd member because its floor is a Namespace annotation or a control-plane setting, and kurly renders neither. **Both this axis's and `network`'s composition guard assert on `self.config.name`, not on `config` existing** — the mixin contributes `config` itself, so a guard asking whether it exists answers its own question and admits everything.
- `migrations.libsonnet` — `migration(name, to, from=null, stage=null, actions=[])` builds one entry of a stageset-controller migration ladder (the serialized `[]Migration` behind `spec.migrationsSourceRef`); a ladder is a plain Jsonnet array of them. Optional fields and empty action lists are pruned. Actions are stageset-controller `Action` objects passed through **verbatim** — kurly deliberately does not model their schema (it would drift against stageset's API).
- `main.libsonnet` — the entry point: exposes the kinds (as functions), `expose`, `security`, `network`, `migrations`, the `list`/`join` helpers, and (via `+ (import './features.libsonnet')`) every feature at the top level (`kurly.store`, …). `production(app, …)` bundles the standard production concerns (exposure, TLS, DNS, a NetworkPolicy allow-list, a resource tier, replicas, a priority class, a PodDisruptionBudget, topology spread, a ServiceMonitor, a mesh) onto a composed app and returns the parts `list` renders — one call for a self-service portal to deploy a tenant instead of re-assembling the recipe. **It CLAMPS what the workload cannot do rather than refusing**: a Deployment owning a volume can never have a second replica (the volume attaches to one node and every later pod stays Pending), and 175 of the catalogue's 256 controller-bearing stages are shaped that way — so `replicas`, `pdb` and `spread` are all reduced to what that workload can actually run, and one profile can be applied across a fleet without the caller re-deriving each workload's storage topology. A ReadWriteMany claim is NOT taken as permission either: the volume allows concurrency, whether the application survives it is a fact about the application. The same fact is published per stage as **`scaling`** (`topology`: `stateless`/`singleWriter`/`sharedVolume`/`perPod`/`perNode`/`oneOff`, plus `horizontal`), derived by rendering like `posture`, so a portal can explain why a tenant's "make it highly available" did nothing. `list(parts)` wraps manifests in a `kind: List` — the shape a consumer renders a composed workload to. It takes one composed app (its hidden owned manifests ride along) **or** an array assembling several: apps expand to their manifests, bare manifests (a Certificate, a denyAll policy) pass through, sublists flatten, and null entries (`if cond then …` with no else) drop. The `itemsOf` local tells an app from a manifest by the hidden `ownedManifests` an app carries.

**The `+`-feature pattern:** a kind `function(name, image)` returns an object whose hidden `config::` holds all knobs and whose *visible* fields are the manifests, computed from `self.config`. Features are standalone `{ config+:: … }` mixins added with `+`; because manifests derive from the merged config, features late-bind regardless of order, and `std.objectValues(app)` is exactly the manifest set (hidden `ownedManifests::` rides along via `list()`). A workload is authored as `function(params) …` so JaaS can feed parameters as TLAs; `jsonnet` renders the defaults for the artifact pipeline. Two traps:

- Inside a field whose value is a **nested object literal**, `self` binds to that literal, not the app — `base.core` captures `local this = self` for those cases (e.g. `selectorLabels`), and the expose recipes capture `local app = self` for the same reason.
- A feature must contribute **only** to `config`, never patch a manifest field directly — otherwise a later feature that recomputes that manifest from config would clobber it.

**Render-time feature exclusion:** a feature that must not co-occur with another adds its name under a shared group in `config.exclusive` (e.g. every `expose.*` recipe does `config+:: { exclusive+: { exposure+: [name] } }`); a `base.core` `assert` fails the render, naming the conflict, if any group has more than one distinct member. This is how "one exposure per workload" is enforced — the constraint travels with the features, not a hand-written value-flag guard.

**Selector stability:** `selectorLabels` (plus the `name` label k8s-libsonnet's constructors force) feed immutable `matchLabels`; user labels from `withLabels` go to metadata + pod template only. Do not let user labels reach a selector.

**Security defaults:** every kind ships the Pod Security Standards `restricted` profile — every setting is a `config::` knob (runAsNonRoot, seccompProfile, allowPrivilegeEscalation, dropAllCapabilities, readOnlyRootFilesystem, hostUsers) rendered pod-level via `base.core`'s `podSecurity::` fragment and container-level in `container::`. A relaxed knob **omits** its field from the manifest rather than writing the Kubernetes default explicitly — so `security.privileged` output carries no security stanzas at all. Knobs relax two ways: the single-knob hatch features (`kurly.rootUser`, `kurly.writableRootFilesystem`, `kurly.hostUsers`, `kurly.allowPrivilegeEscalation`, `kurly.keepCapabilities`) or the `kurly.security.*` profile mixins (which set all knobs — hatches must compose *after* a profile). **`kurly.addCapabilities(['NET_BIND_SERVICE', …])` grants NAMED capabilities on top of the dropped-ALL default** — the way an app that needs one privilege (a DNS server binding :53) keeps the hardened posture for everything else, instead of keeping every default capability just to get one. `automountServiceAccountToken` (only with an explicit ServiceAccount) is outside both. New workload kinds must merge `podSecurity + podVolumes` into their pod template spec and inherit `container::`; keep the default posture fully `restricted`.

**What booting the whole catalogue taught about images** (the recurring reasons a workload that renders will not run — check these first): an init that drops privileges needs `rootUser + allowPrivilegeEscalation + keepCapabilities` (s6-overlay, su-exec, gosu, and any entrypoint that chowns a volume); an app writing beside its own code needs a `scratch` for that path (or `writableRootFilesystem` where it writes into its install tree); a Service named after the workload makes Kubernetes inject `<APP>_PORT` as a `tcp://` URL, which apps read as their listen port — `kurly.disableServiceLinks` fixes it; the port a stage declares must be the port the image actually binds (a surprising number serve on 8080 as an unprivileged user); a probe that follows a redirect or names a path the app answers 403/404 on kills the pod forever, so probe by connection where the app validates Host or requires auth; a slow first start (migrations, asset builds, plugin relinking) needs `kurly.startupProbe`, not a longer liveness delay. A published image tag can simply be gone — 13 pins were dead when the catalogue was first booted end to end.

## Dependency policy

`jsonnetfile.json` pins k8s-libsonnet to `main`, and `vendor/` + the lock file are **gitignored**: the JOI k8s-libsonnet image tracks upstream HEAD daily, so CI vendoring HEAD tests exactly what clusters run — an upstream break in CI is a wanted signal. Do not commit a lock file or pin a SHA. k8s-libsonnet is **not bundled** into the OCI image; jaas supplies it at render time as its own JsonnetLibrary.

## Tests

`tests/kurly_test.jsonnet` is an assertion suite: every field is a `std.assertEqual` (raises on mismatch), and CI additionally checks all values are `true` via jq. Two negative checks live in the CI test job (`scripts/check-tests.sh`) because jsonnet has no try/catch, so error paths cannot live in the assertion suite: a worker + exposure composition must fail (`requiresService`), and composing two exposures must fail (the `exposure` exclusion group). The examples double as end-to-end fixtures: `hack/validate-examples.sh` renders each one, splits the `List` items, and validates every manifest with kubeconform `-strict` — core kinds against the upstream Kubernetes schemas, Gateway API kinds against the community CRD schema catalog (`-ignore-missing-schemas` covers kinds absent from both, e.g. XListenerSet; watch the summary's skipped count).

## Workload artifact contract

A workload publishes its jsonnet **SOURCE**, not pre-rendered manifests — as a **single-layer** `FROM scratch` vendor-tree image (`/github.com/metio/kurly/workloads/<name>/…`), the exact same build and shape as the kurly library and JOI images. JaaS pulls it (a selector-less Flux `OCIRepository`, since it is single-layer), imports a stage's composable app by its canonical path, composes the consumer's `+` features, and renders with `kurly.list`; stageset deploys the result.

**Why source, not pre-rendered:** a stage is a `function(params)` composable app, so rendering it at release time would bake placeholder defaults (`tik.example.com`, `1Gi`) that no real deployment wants — the consumer's parameters are `+`-composed at *their* render, in JaaS. **Why single-layer, built as an image (not an `oras`-pushed tarball):** a raw `source.tar.gz` layer carries an `image.title` annotation and is consumed as a *file*, not extracted to the vendor tree — JaaS would find no source to import; and a multi-layer artifact needs a `layerSelector`, which a selector-less `OCIRepository` and JaaS's vendor-tree search do not use.

**Maturity and the README deploy section are generated, not hand-written.** Each workload in `catalog.json` carries a `maturity` — a derived `tier` (`rendered` → `tested` → `e2e`) plus two optional axes that are deliberately NOT rungs: an operator-attested `production` record, and a `delivered` record. `gen-maturity` derives the tier into `catalog/maturity.gen.libsonnet`, and `check-catalog` regenerates + drift-checks it, so a tier can never claim more than the repo proves. **`e2e` means VERIFIED, not covered**: every workload has a generated scenario, so deriving the tier from a scenario's existence granted it to all of them and told a reader nothing. The tier comes from `catalog/e2e-verified.libsonnet` — a dated record of the workloads whose scenario actually booted them on a live cluster — and `tested` from workload-specific assertions in `tests/*.jsonnet`; production dates live in the hand-edited `catalog/production.libsonnet`. **`delivered` is an AXIS, not a rung**, and the distinction is load-bearing. `e2e` proves the manifest runs when kubectl applies it; `delivered` proves the whole path a consumer uses — the source image built and pushed, Flux pulling it, JaaS resolving its imports and rendering it, stageset applying it until the controllers roll out. A stage can boot from the checkout and still fail there (a wrong import path renders locally and not from the image), so it is separate evidence: `catalog/delivered-verified.libsonnet`, written by `hack/smoke/deep-run.sh` as it walks the fleet. A custom-resource stage has no controller to roll out and never earns it. **Adding a rung to the ladder is a breaking change for consumers even though `schemaVersion` does not move** — the metio.cloud portal switches on `tier` and falls back to the WEAKEST claim, so an unfamiliar value published as a rung would report the best-proven workloads as never booted. New evidence of a different kind becomes a new axis; only a stronger version of the same claim may become a rung. Every workload README ends with a generated, marker-delimited (`<!-- BEGIN generated: jaas-deploy -->`) section carrying the maturity badge and the full OCIRepository → JsonnetLibrary → JsonnetSnippet → StageSet walkthrough; `gen-readme` splices it in from `catalog/readme.jsonnet` and `check-readme` fails if it drifts. **When adding or changing a workload, write only the README prose above that marker, then run `gen-readme`** — never hand-edit the generated section. `tik`'s README is the hand-authored exemplar the generator is modelled on and is left untouched.

**Each workload also carries its infrastructure requirements in `catalog.json`.** A per-workload `requires` LIST of `{ kind, required, engine?, extensions? }` names the external dependencies a workload cannot supply itself; empty when it needs none. `kind` comes from the closed vocabulary published as `requiresKinds` (`database`, `cache`, `objectStorage`, `broker`) so a consumer validates against it and fails loudly on a term it does not know rather than silently carrying an unpriced dependency. A LIST rather than an object keyed by kind, because a workload can need two of the same kind and an object cannot say so — bigcapital needs a MySQL *and* a MongoDB, and anything provisioning from a kind-keyed object stands up one server, after which the workload never starts. Which kinds a workload needs is hand-annotated; the database `engine` is DERIVED, in the precedence the delivery harness arrived at by being wrong twice: a declared `postgresUrl`/`mysqlUrl` generator in `secretKeys` wins outright (ferretdb speaks the MongoDB *protocol* while storing in PostgreSQL, so reading the protocol takes its database away), then a declared `extensions` (every extension here is a PostgreSQL one), then `MONGO`, then `POSTGRES`/`PG`, then `MYSQL`/`MARIADB` in an env var NAME the stage sets — never prose in a comment, which misclassified 28 of 37 workloads. `engine` is ABSENT where nothing establishes it, which a consumer must read as unknown and never as "the usual one"; 41 of 116 database dependencies state one today. A workload may also state the whole list outright in `annotations.libsonnet`, for what derivation cannot reach. Alongside it, every stage carries a **derived** `storage.pvcs` — the number of PersistentVolumes the stage's default render actually claims (owned PVCs plus a StatefulSet's volumeClaimTemplates), computed in `catalog.jsonnet` by rendering the stage the catalog already imports, so it never drifts. `pvcs: 0` marks a stage that runs without a PVC (state in a database, object storage, or nowhere) — the fleet to filter for an S3-only cluster. A custom-resource stage whose operator provisions storage at runtime (a CNPG Cluster) claims no PVC in its own manifest and reads 0, carrying its dependency in `requires` instead. `requires` is backfilled per workload; `storage.pvcs` is automatic for all. A CR stage may also carry **`pssOperator`** — which PSS bar the pods an OPERATOR actually ran clear, written by `hack/smoke/deep/cr-pss.sh` into `catalog/pss-operator.gen.libsonnet`. A **SEPARATE field from `pss`, never merged**: one is derived from what kurly wrote, the other measured from what ran, and a consumer must be able to tell which it holds — the same reason `e2e` and `delivered` are separate axes. It exists because `pss: null` on a CR stage is correct and unsatisfying: PSS collapses to ONE level and most of it is checked per CONTAINER, so a level computed from whatever pod securityContext a CRD exposes would be a claim about containers kurly never wrote (this is why `posture` CAN answer there and `pss` cannot — posture publishes each knob separately and says `null` for the halves it does not know). Unlike `cr-bsi.sh` it does **not strip the pod**: PSS reads the volumes (hostPath fails baseline, restricted allows eight types), so a stripped pod would come back cleaner than the real one. It needs no API server to judge — the evaluation is jsonnet over a pod spec — so the cluster is only needed to obtain the pods. The verdict is the **weakest** of a stage's pods. An object-level assert refuses an entry for a stage that has since grown its own pod template, since the derived verdict would then be the better evidence. 6 of 17 measured today; the header names why each of the other 11 is absent, split into "there is no pod to look at" (which waiting will not fix) and "we could not ask" (which it would). Every stage carries a derived **`profile`** — what `kurly.production()` actually DOES to it, **rendered by CALLING the function, never written beside it**: a table of recommended settings kept next to the function is a second implementation, and the day the two disagree a consumer previews a deployment that does not happen. It records `asked` (a CANONICAL probe — three replicas, a budget of two, one spread constraint — high enough that every clamp fires, never to be read as advice), `got`, and `clamped`; `clamped` is the interesting half, since without it a reader learns vaultwarden gets one replica and with it learns three were asked for and the software cannot take them. A **null** in `got` means the workload has no such knob (a DaemonSet has no replica count) and is deliberately NOT reported as clamped. 80 stages clamp nothing, 175 clamp all three, and an object-level assert ties `profile` to `scaling` so the two independent derivations cannot drift apart. Every stage also carries a derived **`pss`** — which bar of the published **Pod Security Standards** the stage clears (`level`: `restricted`/`baseline`/`privileged`, plus `violates`, the controls keeping it off the next bar up, named in the standard's own vocabulary so a verdict can be looked up rather than interpreted). Evaluated in `catalog/pss.libsonnet` over every pod template a stage renders and every container in it — regular, init AND ephemeral, because the admission controller checks all three and a privileged init container makes the whole pod privileged. A far more portable claim than `posture` or `bsi`: a versioned public definition every Kubernetes operator already knows, enforced by a controller shipped with the cluster. **kurly's `security.privileged` profile does NOT produce a PSS-privileged pod** — it emits no security fields, which fails restricted (nothing is set) but breaks no baseline control (nothing hostile is set either); the two vocabularies share a word and not a meaning. Today 156 restricted, 98 baseline, 2 privileged (pihole on a capability outside baseline's allow-list, spegel on hostPath + hostPorts). The evaluator lives in its own file so the assertion suite exercises the controls against SYNTHETIC workloads — a rule that long, exercised only by real data, is one whose edge cases nobody has tried — and `podTemplates` moved there with it so both derived facts share one definition rather than a copy that drifts. Each stage also carries a derived **`posture`** — `runsAsRoot` / `writableRootFilesystem` / `ownUserNamespace` / `multiTenantSafe` — computed by rendering the stage and reading its security context, so a portal can refuse or gate the recipes that relax the hardened default before hosting a tenant on a shared node (`null` for a custom-resource stage whose pods the operator runs). And each stage carries **`architectures`** — the linux CPU architectures its pinned image publishes, read from the registry manifest list by `gen-architectures` (skopeo) into `catalog/architectures.gen.libsonnet` and drift-asserted by `check-catalog` (no stale keys); network-bound, so it is regenerated on demand/schedule, not per-PR. A portal reads it to keep an amd64-only image off an arm64 node and place arm-capable workloads on the cheaper burst tier. Each stage also carries a **`signature`** — whether its pinned image has a verifiable sigstore signature and, decisively, whether the signer is the project itself: `gen-signatures` (cosign) verifies the signature, reads the signer's certificate, and records the identity, the OIDC issuer and the source repository the certificate names, into `catalog/signatures.gen.libsonnet`; `catalog.jsonnet` compares that repository against the `upstream` it already derives and publishes `signedByUpstream`. **`signed` alone is not worth a marker in a user interface** — `cosign verify` without an expected identity accepts a signature by anyone, including whoever pushed the image, so only the comparison against the project's own repository says the project released these bits. The claim is anchored to the digest that was measured and goes null the moment the stage's pin moves past it, because a signature covers specific bytes and means nothing carried forward onto bits nobody checked; the entries are therefore drift-asserted for staleness but never for completeness, since a bump invalidates the claim while leaving the key. `signed: false` means asked and answered; ABSENT means nobody asked or the registry refused, never unsigned. Only KEYLESS signatures are measured — an image signed with a long-lived key reads `signed: false`, a known false negative, because there is no discoverable way to learn which key an arbitrary publisher used and trusting one the image hands us proves nothing. Network-bound, so on demand/schedule, not per-PR. Every stage carries a derived **`secrets`** — which Secrets it CONSUMES and how (`as: 'environment'` for envFrom/secretKeyRef, `as: 'file'` with the `path` it is mounted at), computed by rendering. It answers the question a portal asks BEFORE `secretKeys`: is a Secret needed at all. It was added because 12 stages mounted one while declaring no keys, so the catalogue was silent about a hard prerequisite for exactly the workloads that cannot be deployed without a human writing something. The two facts are complementary: `secrets` says WHICH and HOW (derived, cannot drift), `secretKeys` says WHAT TO PUT IN THEM (hand-annotated, since an app's env contract is not derivable). It reports the DEFAULT render, so a stage that wires its Secret only when a parameter names one shows none — 13 declare keys and read no Secret by default, which is legal and not a gap. **A Secret in `secrets` with no matching `secretKeys` is the honest signal that somebody must author its contents**; an object-level assert pins that set EXACTLY (nine today: thanos×3, dex, ente, forgejo, lemmy, misskey, tik) so a new one has to be justified rather than rediscovered. Each of the nine mounts a configuration DOCUMENT no generator can mint — an objstore.yml naming a bucket, a Dex config with connectors — and inventing a `generate: document` would hand a portal a job it cannot do while telling it the job was done. Adding the field immediately found a real omission: `netbox/worker` reads the same Secret as `netbox/server` (its own help says so) and declared none of its six keys, so a consumer minting from the worker's contract alone got nothing. A stage may also declare **`secretKeys`** — the keys the Secret it reads must hold and how to mint each (`{ key, generate: 'password'|'hex'|'literal', length | value }`), so a portal's operator generates tenant credentials from the catalog rather than parsing prose. Hand-annotated per stage (kurly cannot derive an app's env contract), seeded on the launch apps and backfilled from there; kurly still authors no Secret itself.

**Facts a consumer reads, and how each stays true.** Beyond `requires`/`storage.pvcs`/`posture`/`architectures`/`secretKeys`, the catalog carries: `category` (what kind of software a workload is — `application`, `database`, `identity`, `cache`, `search`, `storage`, `messaging`, `networking`, `observability`, `tool`, `admin`; hand-annotated, and `catalog.jsonnet` refuses to build a workload without one), per-stage **`clusterScoped`** (+ `clusterScopedBecause`) — derived from what the stage renders (cluster-wide RBAC, an APIService, a DaemonSet, host networking/namespaces/paths, or nothing but cluster-scoped objects), so "runs for the cluster, not a tenant" is a fact rather than a hand-kept list — per-stage **`bsi`** (which bollwerk policies the stage breaks and the BSI requirements they implement), and per-workload software facts, which are kept deliberately apart from the IMAGE's facts because the two disagree: `image.title`/`image.source`/`image.homepage` are what the image's OCI labels say (`gen-upstream`, network-bound), while `name` is the software's own name (stated in `annotations.libsonnet` or absent — `org.opencontainers.image.title` holds taglines, base images and editions as often as a product name, and a wrong display name is worse than none because nobody can tell it is wrong by looking), and `upstream` is the software's own repository — derived from `image.source` EXCEPT where that is recognisably a packaging repository (`linuxserver/docker-*`, anything named `docker-…`/`…-docker`), since crediting or funding a packager sends it to the wrong people. A workload may also carry a **`description`** — ONE sentence for somebody deciding whether they WANT the software, kept apart from `summary`, which is for somebody deciding how to RUN it (the same separation `consent` and `trademark` earned: a field with an audience must not be quietly reused for another). Absent is a real answer and the common one — a shop would rather show a technical summary than a sentence generated to fill a field. Three rules are ENFORCED in `catalog.jsonnet` rather than documented: one sentence ending in a full stop, never opening with the software's own name (the card already shows it as a heading), and no deployment mechanics or marketing vocabulary — the guard names the offending workload. `license` is checked against the real SPDX register (`catalog/spdx.gen.libsonnet`, written by `gen-spdx` from the list nixpkgs ships, so `check-catalog` reruns it offline and a stale register fails the gate): a label SPDX does not know is dropped and NAMED by `check-catalog` (labels state `ESPHome`, `AGPLv3`, `BSL-1.1`), while an ANNOTATION it does not know fails the build. Alongside it travel `licenseOsiApproved` (a platform selling open source has to see that `BUSL-1.1` is not — this is how emqx's Enterprise/BUSL pin is visible rather than implied) and `licenseDeprecated` (`GPL-3.0` says neither `-only` nor `-or-later`; that ambiguity is reported, never guessed away). `NOASSERTION` becomes `licenseNotAsserted` — a publisher who declined to say is a different fact from nobody having asked, which is what an absent field means. Throughout: a workload's own annotation wins over a label, and an unchecked fact stays ABSENT rather than guessed.

**The BSI verdicts come from an API server, not from reading the rules.** `gen-bsi` installs every bollwerk policy (they live in `bollwerk/` in this repository) with its binding switched to **Warn**, then server-side dry-runs every stage once: Warn returns EVERY violating policy as a warning header, where Deny stops at the first and Audit only reaches the audit log — and nothing is ever rejected, so the sweep cannot leave a cluster that refuses workloads. A stage whose CRD is absent is left out, because "not measured" is not "passed". The `bsi` job in `e2e.yml` regenerates and fails on drift, so a relaxed security knob or an edited policy cannot leave the published claim behind. (The kyverno CLI can evaluate policies offline but ignores their `matchConstraints` here — it reports a PersistentVolumeClaim as violating a ServiceAccount policy — so its verdicts are not publishable.)

A workload carries its version as data: each stage does `local version = std.rstripChars(importstr './version.txt', '\n')`, and the dir holds a `version.txt` committed as `dev` (a data file, licensed via `REUSE.toml`, kept outside the `*.libsonnet` stage globs so no gate treats it as a stage). The release job overwrites that one file with the calver (a whole-file `printf`, no in-place edit) so rendered objects carry `app.kubernetes.io/version`, then builds the shared root **`workload.Containerfile`** — `FROM scratch`, one `ARG WORKLOAD`, one `COPY workloads/${WORKLOAD} …` (one directory → one layer, no staging stage needed) — via `metio/ci/container-release`. A local single-arch build first **asserts exactly one layer** and that the shipped `version.txt` carries this run's version. Editing `workload.Containerfile` re-releases every workload (the discover job treats it as a shared change), since it packages all of them.

## CI

`verify.yml` is the PR gate (fmt, catalog, test, assembler, examples, readme-examples, coverage, security, reuse, yaml, github-actions, markdown, typos, policy, dco), ending in the single `Verify` aggregate job — the only check to mark required in branch protection. Every tool job is checkout → the repo-local composite `.github/actions/nix-devshell` → `nix develop --command <gate>`: the composite installs Nix (`DeterminateSystems/nix-installer-action`) and caches the `/nix` store through the GitHub Actions cache (`nix-community/cache-nix-action`, keyed on `hashFiles(flake.nix, flake.lock)` with a prefix-fallback restore), so the devShell closure is downloaded only when the flake pin changes — every other run restores it in seconds. The tools come from the flake's devShell, pinned by `flake.lock`, never from marketplace actions or `@latest` installs — so CI and local shells cannot disagree on versions. The `dco` job is the one exception (pure git, no tools). `release.yml` does **multi-unit releases from one repository, modeled on metio/helm-charts**: the releasable units are the library (`main.libsonnet` + `lib/` + `Containerfile`), the catalog (`catalog/`), and every directory under `workloads/`. A `discover` job classifies this push's diff per unit (dispatch force-releases one unit or, with empty input, everything — also the recovery path for a failed run, since change detection covers only the push's own range); all units released in one run share a single `metio/ci/calver` version, but each gets its own tag (`library-<version>`, `catalog-<version>`, `<workload>-<version>`), its own GitHub Release, and its own notes via `metio/ci/release-notes` scoped by **`include-paths` and `tag-pattern`** to that unit's files and tag lineage — one unit's commits never leak into another's changelog. The workload matrix runs with `fail-fast: false` so one unit's failure never blocks another's release. The `library` job asserts **exactly one layer** and that the image **renders `kurly.http` from its own tree** (with k8s-libsonnet supplied separately, as JaaS does — so a layer missing `lib/` fails here, not in a consumer's cluster), then publishes via `metio/ci/container-release`; each `workload` job stamps the calver into the workload's `version.txt`, asserts one layer plus the stamp on a local build, then publishes the **single-layer source image** via `metio/ci/container-release` from the shared `workload.Containerfile` (`--build-arg WORKLOAD=<name>`) — the same single-layer discipline as the library. A workload directory must never be named `library` or `catalog` (tag-prefix collision; the discover job fails on it). The `catalog` job publishes `ghcr.io/metio/kurly/catalog` as a **plain OCI artifact** (`oras push`, `artifactType: application/vnd.metio.kurly.catalog.v1+json`), one manifest with one uncompressed `application/json` layer titled `catalog.json`, so `oras pull` alone writes the file and a consumer needs no jsonnet toolchain. It was a `FROM scratch` image so that `COPY --from` could reach it, but the catalogue is data with no platform: the shared release action built it for six platforms whose children all pointed at one blob, none of them carrying a layer title, so `oras pull` fetched every manifest and wrote nothing — a consumer had to walk the index, filter the attestation manifests and fetch the blob by hand. `COPY --from` was never used by anyone; if it is ever wanted it comes back as an additional artifact rather than as a constraint on this one. The job asserts the FILE carries a readable catalog (a `schemaVersion` and a non-empty workload list) before pushing, signs the digest with cosign, attaches build provenance as a referrer, and then pulls what it just published to prove `oras pull` yields a byte-identical `catalog.json`. Its release is gated on `catalog/**` changing: a consumer that pins this image would otherwise get a pull request for every kurly merge, including ones that change nothing it can see. Library changes deliberately do **not** re-release workloads — a workload picks up library changes with its own next release or a forced dispatch, mirroring helm-charts' common-chart handling. Renovate keeps `flake.lock` fresh (the repo-local `renovate.json` enables the `nix` manager + lock-file maintenance on top of the org preset).
